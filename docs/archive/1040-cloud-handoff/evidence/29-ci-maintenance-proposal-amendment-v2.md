# AMENDMENT v2 — Explicit same-head retry through the trusted Full-CI requester

## P01 — Freshness rebuilt on the actual API shapes

**Accepted:** the amendment's freshness inputs were not usable as specified. All three sub-findings are resolved against live API evidence captured today (`probe-matcher-extraction/real-run-35845728143.json`, `real-events-1066.json`, `real-events-1066-headers.txt`).

**A. Completion boundary from the field that exists.** The workflow-run record for the failed attempt carries `status: completed`, `conclusion: failure`, `updated_at: 2026-09-23T10:19:05Z` — and **no `completed_at` property** (verified directly; `has("completed_at") == false`). The rule therefore uses the completed run's **`updated_at` as a conservative completion BOUNDARY**, and says exactly that: it is an update timestamp, not an exact completion timestamp. Its limitation is one-directional and safe: for a terminal run, `updated_at >= actual completion`, and any later metadata touch moves the boundary LATER, which can only cause a refusal — never an undeserved dispatch. The newest-failure boundary is `max(updated_at)` over completed-unsuccessful trusted attempts. Job-level `completed_at` values are not used, so no per-job coverage proof is needed.

**B. Completeness from pagination evidence, not content heuristics.** The "oldest retrieved event is a matching label" heuristic is withdrawn — it would have rejected #1066's real, complete history (five events, whose first IS the September 22 readiness label, followed by the bot unlabel and the September 23 relabel). Completeness is established only from transport evidence: fetch events with header capture (`curl --dump-header`); **complete iff no `Link` header with `rel="next"`**; walk at most a bounded number of pages (3); if a fetched page still carries `rel="next"`, REFUSE (completeness unestablishable — conservative). The real #1066 response is a single page with no `Link` header → complete.

**C. The consumed authorization is the latest live one — not "this run's event".** The inaccurate claim is withdrawn. GitHub gives a workflow run no reference to the label event that created it, so the rule is defined instead as **safe consumption of the latest live authorization**: the requester consumes the latest `labeled(ready-for-full-ci)` event in the COMPLETE history (`E*`, with its GitHub-authored `created_at` and immutable event `id`) as the current live authorization, whatever requester consumes it. **Safety proof (state-machine only, no external marking service):** (1) all same-head requesters serialize in the concurrency group; (2) consuming `E*` means dispatching, which immediately creates a running attempt — every other serialized requester then observes `PENDING` and cannot dispatch; (3) if that attempt succeeds, later requesters bind the found success and never dispatch; (4) if it fails, the failure boundary becomes that attempt's `updated_at > E*.created_at`, so `E*` is stale for everyone and any further retry requires a strictly newer labeled event. Therefore each labeled event authorizes at most one retry, and only when it postdates every observed failure. A queued older requester that reads a newer relabel is safe: it consumes precisely the live authorization; the newer relabel's own requester subsequently observes `PENDING`, an authoritative success, or a stale authorization.

**Freshness rule (unchanged in shape, corrected inputs):** dispatch the single EXHAUSTED retry iff `E*.created_at > newest_failure_boundary` (both parsed as UTC instants); refuse — never guess — when the events read fails, completeness is unestablishable, no readiness-label event exists in the complete history, a timestamp is missing/unparsable, or the comparison is not strictly greater. Freshness gates only the EXHAUSTED retry; `NONE` needs none; binding an existing completed success needs none.

**Required offline cases — all executed today against the real shapes (`probe-matcher-extraction/probe-round2.sh`, results in `probe-round2-results.log`):**

3. *Genuinely fresh request*: same history + 12:00:00Z relabel → **FRESH → one dispatch executed**.
4. *Paginated/incomplete history*: scripted `rel="next"` page → **REFUSE**. **Executed.**
5. *Queued old request + newer relabel*: pre-failure live authorization (09:54:44Z) → **STALE/refuse**; post-failure relabel (12:00:00Z) → **FRESH/dispatch**. **Executed.**

## P02 — Installation is unresolved; the ordinary queue cannot install this change

**Accepted, and stated plainly: installation is UNRESOLVED.** The two stages are distinct: (1) the protected-main requester can qualify a PR head and publish PR-readiness evidence; (2) the merge queue composes a DIFFERENT candidate that needs its own trusted binding — and for that composed candidate the ordinary verifier refuses protected-workflow changes, the maintenance detector explicitly excludes kernel-path changes, and the maintenance preflight returns `separate-trust-root-bootstrap-required`. With those controls unchanged — which this proposal requires — the ordinary queue cannot install this change even with green PR-head Full CI and review approval. The prior "ordinary required checks → merge" promise is withdrawn. **No qualified installation procedure exists today**; the live refusal is the correct present state; this proposal does not weaken any refusal, fabricate any binding, or introduce any bypass.

What remains valid and offered: preparation, exact-candidate qualification through current-main machinery (the requester always executes from the default branch, so a candidate PR's own readiness/binding evidence is produced by pre-change code), and independent review of the exact candidate. The installation step and the trust-root transition that would authorize it are **explicitly out of scope and unresolved** — if a workable route is wanted, it must be designed as a separate, executable, separately reviewed transition proposal (per DEC-121's activation requirements: explicitly reviewed procedure, exact candidate qualification, owner approval of live actions and restoration steps, verification of unchanged required publishers and the main-only secret boundary; unconfigured environment = refusal). The **revert shares the identical installation constraint** and is acknowledged as such: an exact revert of the two files is itself a kernel change and cannot be installed by the ordinary queue either; any future transition design must cover revert as a first-class case.

**Wording corrected:** the requester does mint a check — it obtains the Merge Authority App token and publishes the `Trusted merge-queue binding` check. Preservation requirement restated exactly: that existing controlled publication path (App-token mint + check publication, re-validated against the queue-exclusion guard) is preserved byte-identically; what the requester must never mint remains a product-evidence check (`external_id` `aerolink-product-evidence:pull-request` stays forbidden by the existing contract test).

## P03 — Boundary-validated identity, direct pinned-run polling, restored refresh/NONE row

**A. Terminal-first discovery accepted.** Pinning by PENDING alone rejected a legitimate success (`EXHAUSTED 100 → dispatch → old EXHAUSTED 100 → FOUND 101 success`, and `NONE → dispatch → FOUND success` directly). Corrected rule: at decision time the caller records `boundary_id` = the highest trusted attempt id among matches (0 when `NONE`). Every post-dispatch observation is validated against the boundary: an observation with `id <= boundary_id` is pre-dispatch history (discovery — sleep); the **first observation with `id > boundary_id` establishes `pinned_run_id`**, even when that first observation is already terminal (a completed success binds; a completed failure exits 1 naming it). No legitimate completion is rejected for never having been seen running.

**B. Once pinned, the pinned run governs — not the global matcher.** After `pinned_run_id` is established, decision polls query that run **directly** (`GET /repos/{o}/{r}/actions/runs/{pinned_run_id}`) instead of re-running the global matcher: `status != completed` → sleep; completed success → qualification and binding use exactly that run (the existing jobs fetch already targets `$api/actions/runs/$run_id/jobs?filter=latest`; the summary additionally records the bound run's id and its `run_attempt` from the run record, so attempt identity is explicit); completed unsuccessful → exit 1 naming the pinned id and conclusion. Global-matcher selections continue only before pinning. Two conservative refusals are added: a direct poll whose record is absent/changed (404, head_sha/ref/PR association no longer matching) → refuse (identity unresolvable); any newly observed trusted attempt with `id > pinned_run_id` while pinned → refuse (ambiguous authority / unexpected identity change — never auto-adopt a different run). The probe demonstrates the multi-run case: global selection over {100 failed, 101 success, 105 newer-failed} reports `FOUND 101 success` (success precedence), while pinned-direct polling of a running 101 ignores the newer 105 entirely.

**C. Refresh/NONE row restored.** A refresh-lane requester that finds no trusted run does NOT dispatch; it retains its bounded wait for the separate dispatcher, with the same transitions: discovery `NONE` → sleep; `PENDING <id>` → pin, sleep; pinned success → bind; pinned failure → exit 1 promptly — `boundary_id=0` means the dispatcher's attempt is always pin-eligible. No path dispatches from a refresh lane.

**Executed probe results for these paths** (`probe-round2-results.log`): terminal-first (`poll1: FOUND 101 success`, boundary 100 < 101 → pin + bind, no PENDING ever observed); NONE-dispatch failure and refresh/NONE (`NONE → no dispatch`, transitions per the table); multi-run pinning (`FOUND 101 success` globally with a newer failed 105 present; pinned-direct semantics with the two refusals stated); A/B schedule dispatch counting (2 total, both freshness-authorized).
